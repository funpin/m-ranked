## Основные исправления

- Независимый [reconciliation](../bridge/reconciliation.py) читает фактические
  canonical tables; [projection oracle](../bridge/PROJECTION_RECONCILIATION.md)
  вызывает исходные legacy endpoint calculations. Проверяются полные ordered
  representations, а не повторно скопированные source hashes или одни суммы.
- Corrections сохраняются как новые immutable observations с lineage;
  valid/invalid/unsupported и NULL/zero хранятся отдельно для каждой метрики.
  Raw evidence доступен с проверкой содержимого в установленный retention.
- Archive DROP требует общего DB fence, повторной проверки полного digest и
  off-primary attestation. Реальные тесты конкурентной записи и восстановление
  исторического CSV после удаления **собственной тестовой** raw partition проходят.
- Query/cache revision, DTO и ETag согласованы в одной RR transaction; published
  formula защищена для OLD и NEW parent; чтение raw history у api_read запрещено.
- [Admin catalog](../../backend/ADMIN_CATALOG.md) сохраняет CRUD, matrix,
  enable/disable, native ID, delete confirmation, CAS, replay, CSRF и RBAC.
  Исходные allowlisted команды и identity-входы collectors durably сохраняются
  перед canonical commit и используются независимым history oracle.
- V28 даёт migration verifier SELECT на принятые command receipts. V29 исправляет
  найденный реальным HTTP rehearsal переход native ID после удаления: следующий
  admin interval начинается после последней границы всей истории, даже если
  предыдущий collector timestamp был в будущем. Старые строки не меняются.
  Collector timestamps сохраняются исходными; устаревший повтор отклоняется.
- Legacy CSV сохраняет lexemes, nullable values, order и формат строк, включая
  archived source/native/old-cold facts. Official M-Rating разделяет rank вуза и
  аккаунта. V27 сохраняет историческую аналитику отключённых non-Telegram accounts.
- Overview сохраняет точные legacy статусы провайдеров и аккаунтов. Safe integration
  configuration участвует в representation/cache identity, поэтому её изменение
  при прежней PG revision не оставляет устаревшую карточку под прежним ETag.
- Проверка rollback выявила преждевременное открытие legacy POST до reverse drain.
  Добавлена отдельная rollback-freeze фаза: все чтения legacy, изменения закрыты;
  останавливаются target API и collectors, затем выполняются drain/verify/stop и
  проверка health, после чего открываются legacy формы и запускается collector.
  Actual Nginx дополнительно выявил асинхронность reload: старые workers могут
  обслуживать прежние маршруты после возврата команды. Проверка ожидания завершения
  предыдущего поколения workers реализована и проверена; одного успешного reload мало.

Все SQL-изменения additive: исходные V1–V8 побайтово совпали с указанным HEAD.
Полный [manifest V1–V29](schema-manifest-v29-20260906.md) содержит ссылки на SQL,
SHA-256 и Flyway CRC32; [машинный manifest](schema-manifest-v29-20260906.json)
сохраняет отдельное подтверждение исходных V1–V8.

## Текущая маршрутизация и шаги эксплуатации

```text
Production clients → existing Nginx/HAProxy → legacy FastAPI/Jinja2
Legacy collectors + legacy admin → SQLite (authoritative)

Local/shadow checks:
accepted SQLite snapshots → bridge → PostgreSQL projections → Spring /api/v1 → Next
isolated target collectors + target admin → PostgreSQL + original input receipts
PostgreSQL compatibility projection → isolated recoverable legacy SQLite
```

Production public routes и `/manage` целиком принадлежат legacy. Local browser
forms используют отдельную mutating DB; visual/performance corpus остаётся R30.
Все девять projection states должны быть ready на одной revision; отсутствие
одной projection закрывает deploy/publish/restore/cutover gates.

Пошаговые команды с обязательными preconditions сохранены в
[DEPLOY](../../operations/runbooks/DEPLOY.md),
[CUTOVER](../../operations/runbooks/CUTOVER.md),
[ROLLBACK](../../operations/runbooks/ROLLBACK.md),
[BACKUP_RESTORE](../../operations/runbooks/BACKUP_RESTORE.md) и
[IDENTITY_RECEIPTS](../../operations/runbooks/IDENTITY_RECEIPTS.md).
Они включают locks/drain, SQLite Backup API, полный S_final, fsync, exact schema,
reconciliation, writer ownership, terminal journal и повторный cutover.
В production их не запускали. Reverse report protocol — v4; journal format — v3:
это разные версии разных контрактов, они не должны механически совпадать.

1. Требуются approved production-size clone/capacity run, реальные captures всех
