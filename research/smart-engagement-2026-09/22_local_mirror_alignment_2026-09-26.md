# Локальный стенд: устранение отставания и предел точного совпадения с сервером

Срез 26.09.2026. Этот документ дополняет [исследовательский итог](20_research_conclusions_and_next_actions.md) и уточняет [исторический отчёт о M0/M1](21_fixin_implementation_and_m1_pilot.md). Изменения сделаны **только локально в `fixin`**. На рабочих хостах не выполнялись миграции, деплой, перезапуск или запись в базу.

## Диагноз

1. Перед проверкой локальный `fixin` стоял на старой истории: на 29 коммитов впереди и на 55 позади `origin/fixin`. Локальная БД была практически пустой. Поэтому даже исправно собранный интерфейс выглядел старым и не показывал текущие посты. Safari дополнительно не загружал CSS/JS на локальном HTTP из-за `upgrade-insecure-requests`.
2. `origin/fixin` обновлён до `18896ae`. Это новая архитектура API, фронтенда и анализа аномалий v2. Старое исследование и локальный код сначала зафиксированы коммитом `0aa3dfb`, а затем сохранены в резервной ветке `codex/fixin-pre-sync-20260926`. Рабочий `fixin` переставлен на `18896ae` **без push**. Папка исследования, офлайн baseline, извлечение контекста соседних постов и исправление CSP перенесены поверх новой базы.
3. Активный релиз витрины имеет короткий SHA `924aa8d`; профиль сборщика использует другую ревизию. По read-only проверке хешей релиз витрины отличается от `origin/fixin` ещё примерно 33 файлами, в том числе файлами веб-интерфейса. Коммит `924aa8d` отсутствует в локальном Git и доступных ветках `origin`; прямой fetch этого ref не удался. Поэтому обновление из GitHub само по себе **не даёт побайтовую копию текущего серверного релиза**.
4. Автоматическая проверка доступа отклонила копирование исходников активного релиза на локальный диск, включая ограниченный список проверенных файлов: ранее согласованный read-only аудит production не сочтён явным разрешением на экспорт потенциально чувствительного исходного кода. Никакого обходного копирования не выполнялось. Для точного выравнивания кода требуется отдельное явное разрешение владельца на экспорт согласованных файлов в локальный `fixin` с последующей проверкой diff. До этого точное совпадение UI с сервером не подтверждено.

## Работающий локальный просмотр

- `Makefile` теперь собирает x86_64 API/web на ARM Mac отдельным шагом и запускает Compose без глобального x86_64 override, чтобы PostgreSQL использовал свой ARM-образ. `MRANKED_COMPOSE_PROJECT` одинаково применяется для запуска и остановки.
- `frontend/lib/api.ts`, `frontend/lib/emoji-route.ts` и `frontend/proxy.ts` используют необязательный `PUBLIC_API_BASE_URL` для **публичных GET**. Админский `frontend/lib/manage-facade.ts` и `frontend/lib/catalog-api.ts` продолжают использовать локальный `API_BASE_URL=http://api:8080`. Режим включается в `infra/compose.local.yaml`; по умолчанию публичный клиент тоже локальный.
- Для данной машины прямой выход контейнера к публичному API оказался недоступен. Локальный операторский туннель даёт публичные GET-ответы; детали доступа хранятся только в частных заметках оператора. Инструкция для локального режима: [infra/local/README.md](../../infra/local/README.md).
- Локальная страница вернула HTTP 200 и HTML с текущими вузами и постами. В браузере проверены оформление, карточки и данные: например, у РУТ показан опрос 26.09.2026, 19:38:36 МСК. После исправления CSP на HTTP CSS/JS не переводятся на несуществующий HTTPS-порт; HTTPS-политика остаётся строгой.
- Туннель может кратковременно сбросить отдельное соединение; повторный GET `/api/v1/revision` прошёл. Такой режим зависит от сети и не является постоянной локальной копией данных. Значения на разных страницах могут относиться к разным ревизиям живой базы; локальная БД остаётся пустой.
- На обычной карточке Telegram-поста этого стенда работает [контекстная проверка позднего роста](23_local_neighbor_preview_2026-09-26.md). Она сравнивает текущие сигналы со старыми постами того же канала и новыми публикациями, не меняя сохранённый статус. Отдельная демонстрационная страница удалена. Вывод относится к текущему `fixin` и публичным GET-данным, а не к побайтовой копии серверного интерфейса.

## Проверки и оставшаяся работа

- Docker API/web собран, Next.js TypeScript build прошёл. На обновлённой ветке: `tsc --noEmit` успешно; 12 API unit-тестов, 7 браузерных CSP-тестов, 5 офлайн тестов исследования пройдены; `git diff --check` чистый. Локальные контейнеры `mranked-current-{postgres,api,web}` запущены, веб здоров.
- M0 poll-receipts из коммита `0aa3dfb` **не перенесён** в нынешний `fixin`. Старая миграция имела номер `0030`, который в новой архитектуре уже занят `0030_transfer_attempt_window.sql`; перенести её как есть нельзя. На сервере существует и более поздняя `0042_dataset_revision_retention.sql`, отсутствующая в `origin/fixin`. До адаптации к новому collector/transfer и перенумерации безопасная версия M0 хранится только в резервной ветке. Утверждение в [21](21_fixin_implementation_and_m1_pilot.md) о «M0 готов в текущем `fixin`» относится к предыдущему срезу и теперь историческое.
- Публичный интерфейс показывает живые данные, но локальная админ-панель работает со своей пустой БД. Из неё нельзя размечать существующие production-посты, и этот режим не предназначен для проверки записи/снятия меток на них. Для такого теста нужна отдельная малая локальная фикстура или явно разрешённая копия данных; полный сырой экспорт не входит в согласованный исследовательский объём.
- После явного разрешения на экспорт исходников: сравнить только относящиеся к продукту файлы активного релиза, перенести изменения в `fixin`, проверить зависимости и миграции, затем пересобрать локальный стенд и повторить браузерные/контрактные тесты. Удалённый production не изменять.

## Вывод для следующих агентов

Сейчас можно оценить **свежие публичные данные и обновлённую из GitHub архитектуру** на локальном URL. Нельзя называть стенд точным клоном активного серверного релиза и нельзя считать M0 включённым в текущий `fixin`. Главные нерешённые задачи — согласованный перенос server-only исходников и безопасный порт M0 поверх новой схемы.
