## 1. M0: факты успешного опроса отдельного поста

Подготовлены [миграция](../../db/migrations/0030_bounded_publication_poll_receipts.sql), [политика](../../collector_target/poll_receipts.py) и [код записи](../../collector_target/repository.py). По умолчанию механизм выключен. Явный список `PUBLICATION_POLL_RECEIPT_ACCOUNT_IDS` ограничен 16 UUID. На аккаунт выбираются не более 16 новых реальных публикаций возрастом до 7 суток. Успешное чтение с неизменившимся значением записывается не чаще одного раза за 15 минут на пост; старые записи удаляются пачками по 1000 после 7 суток. `NULL` и качество метрик сохраняются. Факт чтения **не является** фактом пользовательского просмотра.

Теоретический максимум для полностью занятой когорты — `16 × 16 × 96 = 24 576` новых строк в сутки, `172 032` строк за 7 суток без учёта удаления. Это верхняя граница строк, а **не** измерение bytes/RSS/CPU/WAL. Перед любым включением нужны локальные измерения размера строки и индексов, latency и пиков памяти; затем можно начать с существенно меньшей когорты. Не добавлять 16 аккаунтов автоматически: пользовательский ресурсный лимит хостов [зафиксирован здесь](14_host_resource_budget.md). Существующая change-only таблица снимков не меняет семантику. Пропуск строки вне разрешённой когорты означает неизвестность. Внутри когорты пустой bucket тоже не доказывает неудачу или ноль: collector мог не прочитать пост, процесс мог не работать либо измениться состав 16 новейших.

Это покрывает **успешные** post-level reads и случаи неизменившихся счётчиков. Не реализован отдельный лог попыток и ошибок каждого поста: при ошибке batch нет достоверной пары `(post, attempted)`. Для H11 нужно строить risk set только из **пар последовательных успешных receipts одного поста**, с известной длиной интервала, качеством обеих метрик, изменением состава когорты и release events внутри. Нельзя выводить нулевой прирост из отсутствия receipt.
Когорта возрастом до 7 суток предназначена прежде всего для H10/H11 и **не проверяет H7** про ежедневный рост большого старого архива. Для H7 позже понадобится отдельная ещё более узкая рамка старых публикаций и её собственный расчёт ресурсов; расширять текущую когорту молча нельзя.

## 2. M1: офлайн baseline и первая проверка переноса во времени

[Модуль](../../anomaly_analysis/research_baseline.py) — намеренно простой, не подключённый к публичному скорингу прототип. Для каждого поста в фиксированном возрастном окне он моделирует две величины:

```text
yV = log(1 + views)
yR = log(1 + reactions) − log(1 + views)
ŷ = median_platform + shrunk_account_effect + shrunk_format_effect
score = max(|yV−ŷV|/sV, |yR−ŷR|/sR)
p_emp = (1 + #{calibration scores ≥ score}) / (n_cal + 1)
```

`s` — robust MAD scale с нижней границей 0,2. Shrinkage не является научно подобранной оптимальной формой; это проверяемая дешёвая baseline. Ранг `p_emp` следует схеме [Bates et al., 2023](https://doi.org/10.1214/22-AOS2244) для проверки выбросов, но её формальные гарантии здесь **не переносятся автоматически**: временные и аккаунтные наблюдения зависимы, калибровочная группа не является проверенной группой обычных постов. [Oliveira et al., JMLR 2024](https://jmlr.org/papers/v25/23-1553.html) отдельно изучают условия для невыборочной/временно зависимой split-conformal калибровки; наш скрипт не реализует их поправки. Поэтому `p_emp` — ранг относительно *этой калибровочной выборки*, не вероятность накрутки, не вероятность правоты статуса и не гарантия на изменившемся во времени распределении. Одна платформа и один горизонт — отдельная модель. Для RuTube нулевая масса реакций делает такой компонент грубым; нужна two-part проверка из [проекта M1](03_model_design.md).

Протокол и ограниченный read-only [SQL](sql/h123_fixed_age_panel.sql): хеш-выборка максимум 12 аккаунтов на платформу, 1 964 поста 29.08–11.09, исправленные несинтетические снимки около 24 часов и 14 суток. Подробный CSV оставался во временной локальной директории; в проект попали только [14d-агрегаты](evidence/m1_fixed_age_14d_calibration_2026-09-26.json), [24h-агрегаты](evidence/m1_fixed_age_24h_calibration_2026-09-26.json) и [скрипт](scripts/evaluate_m1_fixed_age.py). Временное разделение: fit до 02.09 UTC, calibration 02–04.09, test с 05.09. Даты выбраны после разведки данных, поэтому test отделён от fit/calibration, но **не** является нетронутым проспективным holdout.

| Площадка | 14d fit/cal/test | Доля `p_emp≤0,05` на поздней неделе | Доля `p_emp≤0,01` | 24h fit/cal/test |
|---|---:|---:|---:|---:|
| Telegram | 139/132/281 | 17/281 = 6,05% | 0/281 | 0/0/228 |
| VK | 109/129/216 | 13/216 = 6,02% | 6/216 = 2,78% | 0/0/163 |
| MAX | 141/148/207 | 9/207 = 4,35% | 7/207 = 3,38% | 0/0/177 |
| RuTube | 48/77/184 | 3/184 = 1,63% | 0/184; минимальный достижимый ранг 1,28% | 0/0/128 |

Это доля **хвостовых флагов, не ложных тревог**: независимой истины по этим постам нет. Расчёт Wilson в JSON предполагает независимые посты и потому **не должен** применяться как верхняя граница публичного false-positive rate: посты кластеризованы по 7–12 аккаунтам. Все 7 сильных MAX-флагов относятся к **низкому числу реакций относительно просмотров** и лишь к 2 аккаунтам; из этих агрегатов нельзя выводить искусственный охват. Шесть VK-флагов затрагивают 3 аккаунта и неоднородны по направлению (3 высоких охвата, 2 низких реакции/просмотры, 1 высокий реакций/просмотры). Эти результаты скорее выявляют сдвиг условного распределения и зависимость постов внутри аккаунта, чем готовое правило «сложной накрутки». Даже 5% уровень не подтверждён без cluster-aware проверки. На 24h в fit/cal были публикации (например, 159/132 Telegram), но пригодных точек оказалось 0 — историческая ранняя модель на данном окне не обучается. `insufficient_data` — корректный результат, пока не накоплен новый проспективный период.

## 3. Что это означает для сложных признаков

1. **МФТИ №11342.** По [проверенным интервалам](09_neighbor_post_spillover.md) новые №11343 и №11346 попадают внутрь окон позднего прироста; модель, смотрящая только на старый ряд, пропускает важную условную переменную. Добавлен [офлайн извлекатель интервального контекста](../../anomaly_analysis/neighbor_exposure.py): он требует пары реальных успешных чтений, полной хронологии публикаций, явного максимального разрыва и возвращает новые посты внутри окна вместе с расстоянием в ленте. Равные округлённые значения **не** становятся доказанным нулём. [Регрессионный тест](../../tests/test_neighbor_exposure.py) моделирует первое окно МФТИ, неполную ленту и точный/округлённый ноль. Без накопленных receipts нельзя оценить частоту нулевого прироста, а без платформенно-отдельной модели нельзя задать численный «нормальный перенос». Поэтому этот код **не включён в публичный детектор**.
2. **Канал.** Кластерные посты нельзя считать независимыми. Будущая канальная статистика должна учитывать число eligible постов, положительные и отрицательные условные остатки, совместное событие и эффективное число проверок; сильный каналовый статус без независимой разметки не оправдан.
3. **Между площадками вуза.** [Аудит H9/H13](16_cross_platform_feasibility.md) показал 51 вуз с активностью во всех четырёх сетях, но пустой контентный архив и 19 343 неоднозначные пары ±3 ч. Возможен агрегат `вуз×день/неделя` после калибровки четырёх M1. Post-level event matcher требует подтверждённого контентного ключа и слепой оценки точности связки. Прототип M1 выше не прошёл этот gate, поэтому численный межплатформенный score сейчас был бы фикцией.

## 4. Проверяемые ворота и следующий шаг

- Локально проверены **96 тестов одним запуском** (`test_config`, `test_target_collectors`, `test_research_baseline`, `test_neighbor_exposure`, `test_anomaly_analysis`); `git diff --check` чистый. После первого реального PostgreSQL integration-прогона устранено лишнее требование `UPDATE` для cleanup; повторный тест **2/2 прошёл**, включая receipt и идемпотентный replay. На чистом локальном bootstrap подтверждены таблица `0030` и права `collector_ingest`/`analytics_worker`. Следующий gate — более длительный нагрузочный тест bytes/row, RSS/CPU/WAL при малой когорте; `0030` не включается в production автоматически.
- [Локальный стенд](../../infra/local/README.md) был поднят из прежнего `fixin` в Docker Compose project `mranked-local` на loopback. Контейнеры работали, веб вернул HTTP 200, API `/api/v1/health/live` и `/ready` — `UP` после одной стартовой ревизии **только в локальной пустой БД**. Реальные production-публикации туда не переносились; UI тогда не показывал МФТИ №11342. TypeScript `pnpm typecheck` прошёл. На ARM Mac Docker-сборка по умолчанию не проходит Python lock, который явно закреплён для Linux x86_64; стенд успешно собран с `DOCKER_DEFAULT_PLATFORM=linux/amd64` через эмуляцию, без подмены хешей. Хостовый Next.js build упирался в сетевую загрузку Google Fonts внутри sandbox, но Docker build завершился успешно. **Текущий** стенд и новый read-only просмотр описаны в [22](22_local_mirror_alignment_2026-09-26.md) и [23](23_local_neighbor_preview_2026-09-26.md).
- После первого просмотра в Safari обнаружено, что локальная страница оставалась без оформления: её CSP `upgrade-insecure-requests` переписывала ссылки на CSS/JS в HTTPS, где нет TLS. В `frontend/proxy.ts` директива теперь добавляется только для HTTPS-запроса или доверенного `X-Forwarded-Proto: https` от production Nginx. Локальный Docker-образ пересобран, страница визуально проверена в Safari, вычисленный стиль навигации — `sticky`, 7 проверок `csp.spec.ts` прошли. При эмуляции HTTPS через заголовок директива остаётся на месте; удалённый production не менялся.
- Моментный `docker stats` на **пустом локальном** стенде: web 138 МиБ, API 64 МиБ, PostgreSQL 53 МиБ, CPU около нуля в покое. Это не замер collectors/receipts под нагрузкой и не переносится на лимиты рабочих хостов.
- На локальном стенде провести измерение bytes/row, CPU, RSS, WAL в ограниченном эксперименте перед любым решением о сборе новой когорты. Ограничения рабочих хостов остаются жёсткими; **никакого деплоя или миграции на них без нового отдельного решения**. Локальный стенд не заменяет замер нагрузки на этих хостах.
- Накопить 24h train/cal/test и последовательные receipts, затем оценить M1 с календарём, возрастом/форматом/каналом и two-part RuTube. Проверять калибровку по аккаунтным блокам и во времени, а не только общий процент постов.
- Обогатить [слепой B01](annotation/README.md) локальными результатами отдельно от карточек для ревьюера; нужны два независимых прохода и вероятностная выборка для публичной доли ложных тревог. Админское добавление/снятие только через авторизованную панель по [спецификации](07_admin_review_spec.md), пока код интерфейса не внесён.
- Только после этих ворот проверять вклад H10/H11, реакций `R|V`, канального и вузовского уровня против baseline на новом периоде. Отдельно показать, сколько сильных флагов №11342 снимаются при условии выхода соседей, не объявляя весь пост нормой по одному объяснению.

**Вывод:** M0-код готов для локальной проверки, M1 дал полезный отрицательный результат о калибровке и ранних данных. Публичные сильные статусы, новая модель канала и межплатформенные выводы на этом шаге не активированы.
