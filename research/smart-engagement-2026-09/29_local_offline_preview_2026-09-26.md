# Локальный офлайн-предпросмотр и уборка файлов

Состояние на 26.09.2026, ветка `fixin`. Production не менялся. Этот файл продолжает [протокол недоступного источника](28_local_preview_data_blocker_2026-09-26.md). Это **замороженный частичный срез реальных сохранённых показаний**, а не текущий production и не его зеркало.

## Что работает

- Локальный `web → api → PostgreSQL` обслуживает обычные страницы [сравнения](http://127.0.0.1:3000/compare?platform=telegram&period=30d) и [МФТИ №11342](http://127.0.0.1:3000/publications/26782437-05ec-5040-8313-3cb8fbf5eaff). Оба маршрута дали HTTP 200. В интерфейсе показана короткая метка «Локальный срез».
- В одноразовую локальную БД внесены 10 близких постов МФТИ и 1337 сохранённых **просмотровых** наблюдений. Посты опубликованы 11–15 сентября, наблюдения покрывают 12–15 сентября. Исходный кейс и обоснование окон — [проверка №11342](23_local_neighbor_preview_2026-09-26.md). Для 14.09 окно содержит №11343/11344 и рост старых 2/2; для 15.09 — №11346 и рост старых 5/5. Окно 17.09 есть в сохранённом исходном анализе, но **не имеет ряда в локальном срезе**, поэтому на карточке отображается «1 без данных» и итоговый контекст не считается подтверждённым.
- После загрузки явно выставлено `historyCompleteness=incomplete` для всех десяти записей: ни отсутствие точек после 15.09, ни отсутствие реакций нельзя толковать как отсутствие роста. Сохранённый исходный статус №11342 остаётся историческим результатом анализатора; локальное сравнение не меняет его в БД.
- В [загрузчике](scripts/seed_local_mipt_preview.py) целевая БД зафиксирована как локальная одноразовая `mranked_review10` на loopback. Скрипт отказывается объединять срез с чужими публикациями. Источник — отфильтрованная локальная выгрузка, полученная ранее для [анализа соседних кейсов](27_additional_neighbor_cases_2026-09-26.md) по [SQL эффективных снимков](sql/neighbor_study_snapshots.sql). Отбор учитывает последнюю коррекцию бакета, но локальная БД хранит только итоговое значение, без полной истории исправлений. Внешний номер №11340 восстановлен по порядку публикаций, поэтому его ссылка не заполняется; №11341 и последующие проверялись отдельно.

## Как повторить локально

После запуска одноразового локального стека и его миграций загрузите файлы `local_data/mipt_views.csv` и `local_data/mipt_analysis.json` командой:

```bash
rtk .venv/bin/python research/smart-engagement-2026-09/scripts/seed_local_mipt_preview.py \
  --csv research/smart-engagement-2026-09/local_data/mipt_views.csv \
  --analysis research/smart-engagement-2026-09/local_data/mipt_analysis.json
```

`local_data/` намеренно исключена из Git; она содержит фактические снимки выбранных постов. В репозитории остаются запросы, методика и компактные выводы. При отсутствии этих двух файлов скрипт не восстановит значения: заново получать их можно только из разрешённого ограниченного read-only источника. Локальный web должен быть направлен на локальный API (`MRANKED_LOCAL_PUBLIC_API_BASE_URL=`); краткую метку задаёт `MRANKED_LOCAL_SNAPSHOT_LABEL`. Ни одно из этих настроек не включается в production само по себе.

## Проверка и границы

Локальный API вернул HTTP 200 для публикации, истории, сохранённого анализа и сводки сравнения. Сборка Next.js прошла компиляцию и проверку типов. Браузер показал 10 публикаций и два контекстных окна на обычной карточке №11342. Это проверка **работы интерфейса на частичных реальных данных**, а не оценка точности детектора. Другие каналы и платформы в этом стенде отсутствуют. Для 17.09 нужна полная история; для анализа откликов и межплатформенных связей потребуются соответствующие данные.

Убраны только воспроизводимые локальные кэши и артефакты сборки, старые пустые Docker volumes/containers и временные дубликаты экспортов. Сохранены текущий Docker-стек, `frontend/node_modules`, `.venv`, отфильтрованный MIPT-срез и исследовательские файлы. Размер рабочего дерева снизился примерно с 2,7 до 1,8 ГБ; временная директория освобождена ещё примерно на 350 МБ. Никакая production-служба, база или её конфигурация не менялась.
