# Фактический ресурсный бюджет двух рабочих хостов

Read-only снимок 26.09.2026. Команды: `nproc`, `free -b`, `df -B1 -T`, `lsblk`, `docker stats --no-stream`, `docker system df -v`; конфигурация PostgreSQL и крупные отношения — [метаданный SQL](sql/host_db_resource_audit.sql), применённый на обоих серверах через `BEGIN READ ONLY`. Это **моментный срез**, не профиль пиковой нагрузки. Значения Docker `BlockIO` накопительные с запуска контейнера, не скорость I/O.

Оба хоста проверены только на чтение. Параметры подключения хранятся вне публичного репозитория.

## Жёсткие инженерные следствия

1. **Хост сборщика — узкое место для аналитики.** Один vCPU, 512 МиБ для PostgreSQL, 4 МиБ `work_mem`, лимит временного файла 512 МиБ и около 6,8 ГБ свободного диска делают широкие `DISTINCT`, сортировки по многомиллионным снимкам, многократное обучение в БД и полные выгрузки недопустимым планом. Ранние широкие запросы уже достигали `temp_file_limit` ([аудит](02_data_audit.md)). Использовать конкретные `publication_id`, месячную партицию, индекс `(publication_id, observed_at DESC)`, ограничение периода, `statement_timeout`, исправление по bucket **внутри узкого поста**, короткие batch.
2. **Хост витрины имеет больше запаса, но не является аналитической фермой.** PostgreSQL уже использует около 814 МиБ из лимита 1200 МиБ; контейнеры и сборщики делят 2 vCPU и 4,1 ГБ RAM. Долгие тренировки/симуляции не выполнять в рабочем DB-контейнере. Вынести исследовательское обучение на локальную машину/офлайн-экспорт **компактных признаков**, а online scoring сделать ограниченным по памяти и времени.
3. **Не хранить полный журнал каждой успешной попытки чтения поста бессрочно.** Текущие снимки уже занимают гигабайты за месяц. Для проверки H11 исследовательски фиксировать poll opportunity только у заранее назначенной малой выборки постов и в коротких окнах после выхода нового поста, с TTL/агрегированием после опыта. Перед реализацией измерить фактические байты на запись и ожидаемое число записей/сутки; задать лимит диска, чтобы на хосте сборщика оставался запас для WAL, временных файлов и штатных операций. Отсутствие снимка вне такой наблюдаемой когорты остаётся `unknown`, не нулём.
4. **Поток расчёта:** поддерживать компактные per-post признаки и несколько канальных суточных агрегатов инкрементально по новой dataset revision; переоценивать только изменившиеся посты, соседнее окно и затронутый канал/вуз. Тяжёлые симуляции и подбор параметров — офлайн и пакетно; публичный online путь хранит версию модели, предсказательный хвост, качество и объяснение. Для межплатформенной связки хранить только подтверждённые пары/группы событий и их признаки, а не все декартовы пары постов.
5. **Перед кодом нагрузочный расчёт:** пик CPU и RSS каждого worker, дополнительные строки/сутки и байты/сутки, время ключевых SQL на ограниченном sample, задержка скоринга, резерв SSD. Нельзя обещать вместимость модели по одному `docker stats` срезу. Численные бюджеты выставить ниже текущих лимитов и измерить при обычной работе без остановки коллекторов.

Операционная граница: изменение схемы/collector, очистка outbox/партиций и перенастройка памяти — **не часть** этого read-only исследования. Здесь зафиксирован бюджет для проектирования алгоритма, а не разрешение на такие изменения.
