# Метод: что измеряем и как проверяем

## Измерение

Для поста известны накопительные платформенные счётчики и время их чтения. Разность двух чтений — **нетто-изменение за интервал**, а не точное время действий или число уникальных людей. Отсутствие записи в прежнем `change-only` потоке не означает успешное чтение с нулевым приростом. Исправленные версии одного `sampling_bucket` сводятся к последней; synthetic, пропуски, отрицательные исправления, качество и округление учитываются отдельно. `NULL` не равен нулю.

«Просмотр» различается по платформам: Telegram может округлять видимый счётчик и учитывать пересылки/повторные просмотры; VK хранит `wall.views.count`; MAX — счётчик сообщения; RuTube — `hits`. Ни один из них не даёт нам источник перехода к старому посту. Не складывать платформы и не использовать общий порог `R/V`. Источники: [Telegram FAQ](https://telegram.org/faq_channels?setln=en), [Telegram API](https://core.telegram.org/api/views), [схема VK](https://github.com/VKCOM/vk-api-schema/blob/master/wall/objects.json), [RuTube FAQ](https://rutube.ru/info/faq_recommendpromo/).

## Последовательность

1. **M0 — наблюдаемость.** Ограниченный [журнал успешных чтений](../../collector_target/poll_receipts.py) сохраняет значения даже без изменения счётчика. Сейчас opt-in выключен, срок хранения по умолчанию 7 дней, максимум 16 аккаунтов × 16 постов на батч и одна запись на 15-минутный bucket. Покрытие и право поста попасть в набор риска нужны до расчёта долей аномалий. Исторические снимки не восстанавливают пропущенные чтения.
2. **M1 — возрастная норма.** Отдельно по платформе моделировать прирост за фактический интервал с возрастом поста, календарным временем, аккаунтом, форматом, ранним уровнем и расписанием чтения. Кандидат — иерархическая отрицательно-биномиальная модель; для RuTube сравнить с двухчастной моделью из-за множества нулевых реакций. Семейство выбирается по предсказательной проверке, а не по виду отдельных кейсов. Исследовательский [интервальный baseline](../../anomaly_analysis/v2/interval_baseline.py) и [постовые горизонты](../../anomaly_analysis/v2/post_tail.py) пока проще этой полной модели.
3. **M2 — контекст.** Для Telegram и MAX проверять время нового поста, его позицию в ленте, измеренный охват и рост старых соседей. Положение и охват — только косвенные признаки видимости; переходы между постами неизвестны. M2 должен доказать пользу против M1 на будущих данных. Для VK нужен собственный поздний возрастной фон: рекомендательная лента может давать волну через несколько дней без соседнего поста. Для RuTube короткие события часто неразрешимы из-за редких чтений.
4. **M3 — процесс наблюдения.** При необходимости симулировать платформенное округление, исправления, расписание, batch и `change-only`, затем калибровать статистику на **наблюдаемом**, а не идеальном ряде. Источники постановки: [возрастные кривые](https://doi.org/10.1007/s13278-022-00928-2), [условная модель вузовских постов](https://doi.org/10.1080/23311886.2024.2402086), [интервальные процессы](https://jmlr.org/papers/v23/21-0917.html), [информативные времена чтения](https://doi.org/10.1016/j.csda.2010.04.020).

## Один итоговый сигнал

Ранний и поздний горизонты — разные проверки. Для поста учитывать повторные просмотры, метрики и заранее объявленные горизонты; нельзя выбирать минимальный ранг после просмотра результатов без поправки. Исследовательский постовой код использует фиксированные точки 1/6/24 и 48/72 часа, временной выбор интервала и консервативную поправку. При плохом покрытии — `insufficient_data`, при `change-only` архиве — только `shadow_only`. Контекст может ослабить сигнал, но не подтверждает причину роста. Канал/вуз оцениваются только после постового теста, по повторяемости на независимых неделях и платформенным остаткам, с отдельной калибровкой.

Статусы должны означать силу **статистического** отклонения, не вероятность накрутки. Даже полное M0 не позволяет однозначно приписать просмотры новому посту без внешней атрибуции.
