# Ручные пометки и пересмотр: спецификация следующего этапа

Пожелание владельца: авторизованный пользователь админ-панели может отметить пропущенную автоматикой публикацию и снять ошибочную пометку. **В этом исследовательском этапе код не меняется.** Ни один ручной вывод не является утверждением о «накрутке» без внешнего доказательства.

## Что уже реализовано

| Действие | Текущая основа |
|---|---|
| Добавить сигнал по любой существующей публикации, даже если автоматического нет | `POST /api/v1/admin/publications/{publicationId}/anomaly-signals` в [api/routes/analysis.py](../../api/routes/analysis.py); `origin='manual'`, metric, severity, reason, interval, evidence. |
| Пересмотреть существующий сигнал | `POST /api/v1/admin/anomaly-signals/{findingId}/reviews`: `explained`, `unresolved`, `data_error`, `dismissed`; append-only история в [DB-функциях](../../db/migrations/0011_functions_base.sql). |
| Скрыть ошибочную пометку из публичного ответа | `dismissed` и `data_error` делают finding неактивным во [view](../../db/migrations/0012_views.sql); `explained`/`unresolved` остаются видимыми с пояснением. |
| Ограничить доступ | Оба POST-маршрута требуют `ADMIN` и CSRF; текущая сессия — cookie после пароля+OTP, роль повторно проверяется ([security.py](../../api/security.py), [admin.py](../../api/routes/admin.py)). Команды имеют idempotency/correlation, actor и запись аудита. Приватный комментарий не попадает в публичное view. |

Документ [docs/features/anomaly-analysis.md](../../docs/features/anomaly-analysis.md) упоминает HTTP Basic; это расходится с фактическим cookie-session кодом и должно быть исправлено при реализации интерфейса.

## Пробелы

1. В [админ-панели](../../frontend/app/manage/admin-console.tsx) нет экрана/клиента для перечисленных POST; оператору недостаточно одной схемы API.
2. Нет удобного **админского списка и полной истории** сигналов/ревью для выбора `findingId`, фильтра по платформе/каналу, просмотра исходных точек и следа решения. Публичный endpoint показывает лишь активные сигналы и не предназначен для восстановления закрытых решений.
3. На публикацию без finding нельзя записать «проверена, явного сигнала нет», «контекст объясняет отклик» или «данных недостаточно», не создав искусственно **положительный** manual finding. Для исследовательской разметки это плохая схема; нужен отдельный record оценки либо отдельный слой task/label.
4. Нет канального ручного review/заметки и механизма привязки нескольких post findings к одному решению о повторяемом паттерне.
5. Публичный `overallSeverity` берёт максимум **всех** активных finding, включая ручные, а `suspicionScore` — максимум только автоматических ([api/sql/analysis.py](../../api/sql/analysis.py)). [Интерфейс](../../frontend/components/anomaly-analysis.tsx) показывает их рядом; высокий ручной severity может выглядеть как тот же автоматический балл. Следующий UI должен явно разделить источники и основания.
6. Существующий цвет `StatusPill` — состояние обработки `ready/partial/failed`, а не цвет силы аномалии. Новую шкалу силы проектировать отдельно, без слов «99–100%».
7. Кейс [МФТИ №11342](09_neighbor_post_spillover.md) показывает ограничение `explained`: такое ревью сохраняет finding видимым, включая высокий severity. Для **ложного** срабатывания из-за неучтённого соседнего поста админ должен иметь действие `dismissed` с причиной `neighbor_post_spillover` (или иной утверждённой причиной), чтобы убрать именно этот сильный сигнал. Контекст события можно показывать отдельно от активной аномалии. Если остаётся другое независимое основание, его нельзя скрыть тем же решением.

## Требуемое поведение будущего интерфейса

- Войти через действующую админ-сессию, пройти серверную проверку `ADMIN` на каждом действии и CSRF; не создавать отдельный публичный write API и не полагаться лишь на скрытую кнопку. Доступ к чтению закрытой истории также только у авторизованных админов.
- На карточке поста показать **эффективный исправленный** ряд, source revision, quality каждого счётчика, окно неуверенности, automatic findings и их исходные evidence, альтернативы, все прошлые ручные решения. Для канала — список постов и повторяемость, но без подмены независимой метки.
- «Добавить ручную пометку»: метрическая привязка, интервал, нейтральный reason, evidence и комментарий. `origin=manual` и актор должны быть видны; автоматический числовой score от этого не меняется.
- «Снять/исправить пометку»: выбрать конкретный finding и решение `dismissed` или `data_error` с обязательной причиной. Исходный finding и все ревизии ревью сохраняются для аудита; публичная активность обновляется по существующей серверной логике. `explained` означает подтверждённое объяснение **статистически необычного** движения, поэтому сигнал может остаться видимым с явной причиной.
- «Проверено без сигнала / недостаточно данных»: отдельная запись оценки, не manual anomaly finding. Она не должна автоматически менять публичный score. Два независимых исследовательских голоса хранить раздельно от последней операционной команды.
- Отображать автоматическую и ручную степень отдельно; публичный текст сообщает наблюдение и источник решения, но не приписывает намерение. Перед повторной отправкой использовать idempotency key, а при конфликте ревизии предлагать обновить карточку.

## Проверки при последующей реализации

Серверная проверка роли/CSRF (включая прямой вызов без UI), закрытость private comments, запись акторов и истории, обработка отменённого finding при новом пересчёте, корректное разделение score/severity, доступность и сообщение о `insufficient_data`. Настоящее исследование только фиксирует контракт; реализация и тесты — отдельная задача.
