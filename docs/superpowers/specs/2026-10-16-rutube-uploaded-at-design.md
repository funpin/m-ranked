# Дата загрузки видео Rutube (`created_ts`)

## Зачем

Официальный М-Рейтинг (m-rating.ru) считает видео Rutube за месяц по дате
загрузки, а не публикации. С `created_ts` порог «меньше 5 видео — 0» сходится
с официальным в 97 % случаев против 93 % по дате публикации (КГУ Курск, август:
13 видео опубликованы в августе, но загружены в июле — официально 0). Прогноз
М-Рейтинга (ветка `feat/rating-forecast`, спецификация
`2026-10-16-rating-forecast-design.md`) возьмёт эту дату для порога Rutube.

Сейчас `collector_runtime/rutube.py` берёт `publication_ts or created_ts` как
`published_at`, а сам `created_ts` нигде не сохраняется. `published_at` не
меняется: на нём держатся месяцы партиций снимков, окно отслеживания и все
страницы.

## Решение: колонка `ingest.publication.uploaded_at`

`timestamptz NULL`. Заполнена только у Rutube; у прочих площадок `NULL`
(у них нет отдельной даты загрузки).

Почему не `quality_flags`. Флаги входят в семантический отпечаток снимка
(`normalize.py`, `semantic_state`). Новый ключ сменил бы отпечаток у каждого
видео Rutube: по одной лишней строке снимка на видео, а для постов старше
`heartbeat_max_age` — повторно открытый архивный месяц (ADR-016). Кроме того,
дата в jsonb-флагах — не флаг: её пришлось бы разбирать текстом в каждом
запросе прогноза. Идентичность (`publication_identity`) — про внешние ключи,
не про время. Колонка ничего из этого не задевает.

Цена хранения: `ADD COLUMN` без значения по умолчанию — только каталог, без
перезаписи таблицы. `NULL` у остальных 68 тыс. строк места не занимает (битовая
карта NULL у строк уже есть), у ~5 тыс. видео Rutube — 8 байт.

## Поток данных

1. **Сборщик** (`collector_runtime/rutube.py`). `RutubeVideo.uploaded_at` из
   `created_ts` — и в выдаче канала, и в точечном запросе видео. Нет поля или
   оно не разбирается — `None`; пакет из-за этого не отвергается.
2. **Площадка** (`collector_target/platforms/rutube.py`). `rutube_batch`
   передаёт дату в `RawPublication.uploaded_at` (новое поле, по умолчанию
   `None`).
3. **Нормализация** (`normalize.py`). `CanonicalPublication.uploaded_at`
   (новое последнее поле, по умолчанию `None`), приведённое к UTC. В
   `evidence` и `semantic_state` дата **не входит**: отпечатки снимков
   прежние, лишних строк снимков нет.
4. **Перенос S1 → S2** (`transfer.py`). В публикации события — ключ
   `uploadedAt`, только когда дата есть. События прочих площадок байт в байт
   прежние (их `eventId`/`semanticHash` не меняются). Приёмник читает
   `item.get("uploadedAt")`. Старый приёмник неизвестный ключ пропускает
   (хеш считается по телу целиком, разбор — по известным ключам), так что
   порядок выкатки не ломает перенос, лишь теряет дату до обновления S2.
   Конверты, запечатанные старым сборщиком, приходят без ключа — `None`.
5. **Запись** (`repository.py`, одна и та же на S1 и S2). Вставка пишет
   `uploaded_at`; при конфликте —
   `COALESCE(excluded.uploaded_at, current.uploaded_at)`: пакет без даты
   (старый конверт, другая площадка) её не стирает. Колонка входит в проверку
   `IS DISTINCT FROM`, поэтому строка обновляется один раз — когда дата
   появилась, — и дальше запись прежняя (без лишних UPDATE).

## Заполнение существующих видео

Окно отслеживания — 30 суток: видео, опубликованные за последний месяц,
получат дату сами из выдачи канала и точечных запросов сборщика. Старым
(с 01.07, около 5 тыс. на копии прода) нужен разовый backfill.

Сервисы Сервера 2 выпускают сеть только по списку (`IPAddressAllow`), к
rutube.ru они не ходят, а база Сервера 1 до Сервера 2 не доходит. Поэтому
backfill — в два шага, без новых сетевых доступов:

1. `python -m collector_target.rutube_upload_backfill` читает id видео (по
   одному в строке; список — запросом из базы), спрашивает публичный
   `GET /api/video/<id>/` с ограниченной параллельностью (4 запроса) и
   печатает SQL: `UPDATE ingest.publication … FROM (VALUES …)` пачками,
   только где `uploaded_at IS NULL`, сопоставление по
   `publication_identity.external_id` + площадке `rutube`. Запускается там,
   где есть доступ к rutube.ru (ноутбук или Сервер 1). Удалённые видео
   (404/410) пропускаются и считаются в stderr.
2. Получившийся файл применяется через `psql` на обеих базах обычным путём
   миграций (`SET ROLE migration_owner`). Повторный прогон ничего не меняет.

## Выкатка

1. `0083_publication_uploaded_at.sql` на обеих базах (до кода).
2. Код приёмника на Сервере 2 (`collector_target/model.py`, `transfer.py`,
   `repository.py`), перезапуск `m-ranked-target-transfer-ingest.service`.
3. Код сборщика Rutube на Сервере 1 (те же файлы плюс `normalize.py`,
   `platforms/rutube.py`, `collector_runtime/rutube.py`), перезапуск
   `m-ranked-target-collector@rutube`. Прочие сборщики не трогаются: колонка
   допускает `NULL`.
4. Backfill (шаги выше) на обеих базах.

Откат: прежний код; колонка остаётся (`NULL`-совместима), либо
`ALTER TABLE ingest.publication DROP COLUMN uploaded_at`.

На прод — только после явного «делай» владельца.

## Проверка и замеры (AGENTS.md)

- Тесты: разбор `created_ts` (есть, нет, кривой); `rutube_batch` передаёт
  дату; нормализация не меняет отпечатки снимка; перенос туда-обратно с датой
  и без, байтовая неизменность событий других площадок; upsert в PostgreSQL —
  вставка, сохранение при пакете без даты, отсутствие повторного UPDATE;
  генератор backfill-SQL.
- На копии прода до/после: время и блокировка миграции; план и время upsert
  пакета Rutube из 100 публикаций (старый и новый запрос); размер
  `ingest.publication`; размер события переноса Rutube; запрос «видео по
  месяцу загрузки на аккаунт» (то, что будет читать прогноз).

## Не входит

- Чтение даты в API и прогнозе — это ветка `feat/rating-forecast`.
- Часовой пояс Rutube. `created_ts` и `publication_ts` приходят без зоны и,
  как и сейчас для `published_at`, читаются как UTC. Если на деле это время
  Москвы, сдвинуты обе даты на 3 часа; проверка — отдельная задача.
