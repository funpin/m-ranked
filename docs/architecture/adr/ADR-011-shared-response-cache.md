# ADR-011: общий кэш ответов на Сервере 2

- Status: **Accepted, implemented in P2.3**
- Date: 2026-09-20
- Отменяет для профиля B: [ADR-008](ADR-008-no-redis.md)
- Реализация: P2.3 [плана перехода](../two-server-migration-plan.md)

## Context

`ADR-008` убрал Redis 2026-09-13 и разрешил вернуть его «только по измеренной
потребности». Обоснование было верным для своего контекста: один API-процесс на
одном ядре, отдельный daemon без доказанной выгоды.

Контекст меняется дважды.

Во-первых, `api/__main__.py` держит один uvicorn-воркер сознательно — «сервер
держит одно ядро, поэтому воркер один». На Сервере 2 с запасом мощности воркеров
будет несколько, и у каждого окажется свой LRU: память умножается, hit rate
падает, прогрев каждого воркера независим.

Во-вторых, требуется прогревать кэш **до** запроса пользователя, а не при первом
обращении. Существующий `api/cache.py` умеет stale-while-revalidate
(`begin_refresh`/`end_refresh`), но обновление запускает только запрос,
попавший в устаревшую запись.

## Decision

На Сервере 2 общий кэш ответов — Redis. Ключ по-прежнему включает dataset
revision, TTL ограничивает жизнь записи, инвалидация по тегам приходит из
PostgreSQL `LISTEN/NOTIFY` через outbox, как и сейчас.

Добавляется фоновый прогрев: отдельный воркер по расписанию пересчитывает
заранее известный набор горячих ответов (overview, статистика, топовые
учреждения) и кладёт их в Redis до того, как их запросит пользователь.

Корректность не зависит ни от доставки уведомления, ни от доступности Redis.
При недоступности Redis операция считается промахом и API строит ответ из базы:
кэш остаётся ускорением, а не условием работы. Ошибка увеличивает
`mranked_api_cache_redis_errors_total` и не становится ответом 500.

Профиль A (один сервер) Redis не поднимает и продолжает работать на in-process
LRU по правилам `ADR-008`.

## Реализация P2.3

`ResponseCache` и `RedisResponseCache` имеют один контракт `get`, `put`,
`invalidate`, `clear`, `begin_refresh`, `end_refresh`; `serve()` выбирает
текущую revision и строит одинаковый ключ для запроса и прогрева. Вызовы
публичных route-модулей не менялись. В Redis лежат только JSON публичного
ответа, ETag, ограниченные теги и времена жизни. Исходный ключ хешируется
SHA-256; заголовки, cookies, DSN и данные сессий в него не входят. Значение,
похожее на credential, Redis-реализация отказывается записывать.

Право на пересчёт — `SET key token NX PX 150000`. TTL по конфигурации обязан
быть больше `API_STATEMENT_TIMEOUT_MS`; умерший держатель поэтому отпускает
ключ автоматически. Освобождение — Lua compare-and-delete, так что опоздавший
воркер не удалит уже чужой lock. Один и тот же механизм используют живые
запросы и отдельный HTTP-воркер прогрева.

`clear()` Redis-реализации не удаляет общий кэш. Потерявший LISTEN-соединение
процесс перестаёт доверять общей подсказке текущей revision; следующий его
запрос сверяет revision с PostgreSQL и обновляет подсказку. Остальные процессы
и уже прогретые записи не наказываются за чужой reconnect. Если уведомление
потеряно всеми, revision-scoped key и TTL остаются границей корректности.

Прогрев запускается отдельно (`python -m api.cache_warmup`), а его относительные
публичные URL задаются `API_CACHE_WARMUP_TARGETS`. Административные, сессионные,
абсолютные и несущие secret-параметры URL отвергаются при чтении конфигурации.
Каждый target выполняется независимо, поэтому один отказ не прерывает остальные.

## Измерение решения

Локальный probe `benchmarks/response_cache.py` выполнен 2026-09-21 на Apple
Silicon, Python 3.14.7 и одноразовом Redis 8.10.0 в Docker: 500 операций,
256 ответов по 4,088 байта. Miss включает lookup и запись ответа, но не запрос
к БД; это сравнивает только цену кэша.

| Backend | hit p50 / p95 | miss+fill p50 / p95 |
|---|---:|---:|
| in-process LRU | 0.000375 / 0.000459 ms | 0.000666 / 0.000917 ms |
| Redis | 0.541249 / 0.639916 ms | 1.039813 / 1.465917 ms |

После прогрева только первого воркера hit rate первой волны был 100 % у одного
воркера для обоих backends, 25 % у четырёх независимых LRU и 100 % у четырёх
клиентов общего Redis. Измеренная память 256 ответов: LRU 1,123,284 байта при
одном и 4,491,520 при четырёх процессах; Redis server 1,445,016 и 1,452,256
байта соответственно. Это локальная оценка Python allocations и Redis
`used_memory`, не production RSS.

Вывод: для одного процесса Redis не окупается — он медленнее и занимает больше
памяти, поэтому профиль A остаётся на LRU. При четырёх воркерах он добавляет
примерно 0.5 ms на попадание, но сохраняет прогрев между всеми процессами,
поднимает первую волну с 25 до 100 % и не умножает payload memory. На фоне
зафиксированной стоимости перестроения 730–1024 ms это достаточная измеренная
потребность для профиля B; production p95 и RSS всё равно являются rollout
gate развёртывания профиля B.

## Consequences

Возвращаются daemon, credential и режим отказа, которых `ADR-008` избегал. Это
принятая цена за общий кэш между воркерами и за прогрев до первого запроса.

Появляется новый класс ошибок — расхождение Redis и dataset revision. Его
закрывает ключ по revision: запись от прошлой ревизии не может быть отдана как
текущая, поэтому худший случай — промах, а не устаревший ответ.

Production rollout повторяет probe на целевом Server 2 и наблюдает реальные
hit rate, p95, Redis memory и DB load. Если выигрыш общей первой волны там не
подтвердится, Redis не включается, а решение пересматривается.
