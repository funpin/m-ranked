# ADR-010: два профиля развёртывания и граница raw/ready

- Status: **Accepted**
- Date: 2026-09-20
- Дополняет: [ADR-001](ADR-001-modular-monolith.md), [ADR-007](ADR-007-live-bounded-reads.md)
- Реализация: P0–P1 завершены для профиля A; см. [план перехода](../two-server-migration-plan.md)

## Context

Production — один хост с 1 vCPU и 2 GiB RAM. Измерения на нём: PSI CPU 64–78 %,
сборщики 38–60 %, PostgreSQL 10–26 %. Запас исчерпан: `ADR-009` прямо фиксирует,
что каденция 300/300/300/3600 при строгой эксклюзии фазы физически недостижима,
а симуляция суток даёт 70 фаз Telegram из 288 желаемых в консервативном сценарии.

Нужна возможность ставить проект двумя способами: целиком на один сервер и
раздельно, вынеся представление данных на более мощный хост.

Наивная формулировка «Сервер 1 компактно пишет сырое, Сервер 2 показывает
готовое» не выдерживает проверки кодом по двум причинам.

Во-первых, API читает «сырые» таблицы напрямую, а не только проекции:
`ingest.visible_publication` — 16 обращений, плюс `publication_metric_snapshot`
и `_active` для истории графиков, `reaction_breakdown`, `publication_identity`,
`collection_run` и `collection_account_result` для индикаторов пропусков сбора.
Единственная настоящая ready-проекция — `analytics.publication_latest`
(28 782 строки против 4.8 млн снапшотов).

Во-вторых, сборщик сам интенсивно **читает** базу во время цикла: планирование
refresh опирается на `ingest.publication` и `publication_identity`, распознавание
временных обнулений ВК — на `publication_metric_snapshot_active`, история
идентичности — на `catalog.account_external_identity`, состояние удалений — на
`publication_availability_state`. Сервер 1 не может быть write-only журналом.

## Decision

### Граница raw/ready

Граница проходит по тому, **что читает API**. На Сервере 1 остаётся только то,
что API не читает никогда: `ingest.raw_payload`, `ingest.evidence_quarantine` и
source-слепки — самая объёмная и бесполезная для просмотра часть. Всё
остальное уезжает на Сервер 2 в текущей форме.

Следствие: API не переписывается, функциональность не теряется, разгрузка
достигается сразу.

### Состояние Сервера 1

Сервер 1 держит **ограниченный рабочий набор** — ровно то, что нужно адаптерам
для планирования следующего цикла:

- публикации в пределах `TRACK_POST_FOR_HOURS`;
- последний снапшот на публикацию;
- identity-состояние аккаунтов;
- булев флаг `ever_positive` на метрику вместо скана истории снапшотов.

Полная история живёт только на Сервере 2. Флаг заменяет текущий
`metric_ever_positive`, который сегодня отвечает на тот же вопрос обходом
истории.

### Транспорт

Сервер 1 нормализует сам — рабочий набор канонический по построению, — поэтому
envelope везёт **канонические батчи**, а не сырые payload'ы провайдеров.
Валидация и карантин происходят у источника: негодные данные не путешествуют.

Транспорт — envelope/outbox/inbox поверх HTTPS + mTLS. Durable payload хранится в
отдельном `ops_and_admin.transfer_outbox`: `outbox_event` остаётся уведомлением
инвалидации и не подходит для replay. Роль `outbox_worker` переиспользуется только
для транспортных прав (`publish_attempts`, `available_at`, terminal-состояние).
Подтверждением считается durable commit в inbox, а не приём запроса.

### Профили

| | Профиль A: один сервер | Профиль B: два сервера |
|---|---|---|
| Сборщики | локально | Сервер 1 |
| Рабочий набор | та же БД | Сервер 1 |
| outbox → DataAdapter | in-process, без HTTP | HTTPS + mTLS |
| Полная история, API, web, анализ | локально | Сервер 2 |
| Кэш | in-process LRU | Redis, см. [ADR-011](ADR-011-shared-response-cache.md) |

Профиль A использует **тот же** envelope и тот же DataAdapter, только применяет
батч локально и в той же базе. Это стоит одной лишней записи в outbox там, где
можно было обойтись, и покупает один кодовый путь, один набор тестов и один
набор багов вместо двух.

## Consequences

Сервер 1 перестаёт платить за представление данных: уходят чтения API и
аналитики, полная история снапшотов, триггер `publication_latest` и рост диска.
Остаются 38–60 % CPU самих сборщиков — их сетевое ожидание переездом не
сокращается, поэтому каденцию отдельно адресует
[ADR-012](ADR-012-collect-persist-phases.md).

Появляется новая поверхность отказов: outbox, inbox, mTLS-сертификаты и лаг
доставки. Сбор при недоступности Сервера 2 продолжается — батчи копятся в
outbox, — но рост outbox становится наблюдаемой величиной с собственным
порогом.

Возврат к одному серверу остаётся возможен в любой момент: профиль A — это тот
же код с другим значением конфигурации.
