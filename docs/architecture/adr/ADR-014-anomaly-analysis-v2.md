# ADR-014: анализ аномальной динамики v2 — вывод по посту, согласие семейств, защищённые нормы

- Status: **Accepted**
- Date: 2026-09-23
- Зависит от: [ADR-006](ADR-006-anomaly-terminology.md), [ADR-010](ADR-010-deployment-profiles.md)
- Реализация: `anomaly_analysis/v2/`, миграция `0036`, описание методов —
  [`docs/research/anomaly-methods-v2.md`](../../research/anomaly-methods-v2.md)

## Context

Первая модель анализа публиковала ревизию на каждый прогон, три детектора
отвечали одним числом «suspicion score», а отчёт на странице поста был скрыт:
вывод было невозможно объяснить, а хранение росло без пользы для страницы.
Исследование (`docs/research/anomaly-detection.md`) собрало десять паттернов
динамики публичных счётчиков, их формулы и ложные срабатывания, в том числе
честные поздние скачки от пересылок.

## Decision

| Вопрос | Решение | Почему |
|---|---|---|
| Уровень вывода | Только пост; без сводки по аккаунту и без влияния на рейтинг | Вывод по аккаунту требует ручной проверки, которой пока нет; рейтинг не должен зависеть от эвристики |
| Фон сравнения | Пост и его аккаунт, нормы по площадкам; норма площадки — запасной фон при истории короче 20 постов | Универсальной формы нормы нет (исследование, раздел 2) |
| Уверенность | Три градации: слабый сигнал, выраженная аномалия, признаки искусственной активности — последняя только при согласии двух разных семейств | Одно число выглядело вероятностью; согласие независимых методов объяснимо и устойчиво к одному ложному детектору |
| Нормы | Адаптивные, с пятью мерами защиты: абсолютные детекторы первыми, форма из литературы, медиана по аккаунтам, эталон, молодая норма не выносит сильных вердиктов; плюс дрейф с ручным разбором | Иначе систематическая подача вошла бы в норму с первого дня |
| Стек | numpy и scipy, без ML-моделей | Нет размеченной выборки; нужна прозрачная логика с формулой на каждый признак |
| Хранение | Строка вывода на пост и журнал только смен вывода; поле статуса проверки ADR-006 заложено | Странице нужен текущий вывод; история нужна только там, где вывод менялся |
| Показ | Сразу после реализации: свёрнутая карточка, формулы, мини-графики, символы на графиках | Решение владельца; свёрнутый вид не мешает данным |
| Прежние таблицы | Не мигрируются; удаление — отдельная миграция после проверки v2 (`db/migrations/pending/0037…`) | Выводы v1 несопоставимы с v2; откат на v1 должен оставаться возможным до проверки |
| Окно | 30 суток (`TRACK_POST_FOR_HOURS`), расписание по возрасту: 15 мин — 3 ч, RuTube 3–24 ч | Анализ втрое реже сбора — между анализами приходит не меньше трёх замеров |

Изоляция: модуль не импортирует API, сборщиков и перенос, они — его; API
читает одну таблицу `analytics.post_anomaly_state` SQL-запросом в одном
маршруте. Это проверяется тестом `tests/test_anomaly_isolation.py`.

## Consequences

Положительные:

- каждый признак несёт формулу с числами, интервал, масштаб и честные
  альтернативы — вывод можно объяснить и оспорить;
- хранение растёт числом постов, а не числом прогонов;
- бюджет Сервера 2 выполняется с запасом: 0,02–0,05 ядра на ~15–17 тыс.
  анализов в час, 136 МБ памяти (`benchmarks/README.md`).

Отрицательные:

- нормы нужно строить и принимать каждую ночь, а версия на разборе дрейфа
  требует решения человека;
- пока норма молода, признаки относительно неё (2, 4, 5, 10) слабы — первые
  недели сильный уровень дают только абсолютные детекторы;
- админские команды ручных пометок v1 уходят вместе с удалением v1; ручной
  проверки v2 пока нет.

## Alternatives considered

- **Продолжить v1 с новыми детекторами.** Отклонено: одно число и ревизия на
  прогон не решают ни объяснимость, ни рост хранения.
- **Классификатор на признаках.** Отклонено: нет размеченной выборки, и
  классификатор не даёт формулы, которую можно показать.
- **Сводка по аккаунту.** Отложено: без ручной проверки это было бы суждением
  об университете, которое ADR-006 запрещает выносить автоматически.
