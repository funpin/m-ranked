# ADR-013: размещение аккаунтов по сборщикам и слияние наблюдений

- Status: **Accepted**
- Date: 2026-09-20
- Зависит от: [ADR-010](ADR-010-deployment-profiles.md)
- Реализация: не начата; фаза P4 [плана перехода](../two-server-migration-plan.md)

## Context

Профиль B должен допускать несколько Серверов 1 с настраиваемой политикой: чистый
шардинг, шардинг с копиями (например, любые два сервера из десяти ведут одни и те
же аккаунты) и полное дублирование. Политика задаётся централизованно — с
Сервера 2.

Два ограничения делают наивные схемы неверными.

**Учётные данные привязаны к серверу и площадке.** MAX требует user-session с
телефоном и `max.session.db`, Telegram — session-файл или web-профиль. В systemd
это отдельный `LoadCredential` и отдельный пользователь на каждый instance.
Не любой Сервер 1 способен собирать любую площадку.

**Схема допускает одно наблюдение на sampling bucket.** Ограничения:

```sql
UNIQUE (published_month, publication_id, sampling_bucket, source_fingerprint)
UNIQUE (published_month, publication_id, sampling_bucket, correction_sequence)
```

Два сервера, замерившие одну публикацию в одном бакете, дадут разные
`source_fingerprint` — первое ограничение их не схлопнет, второе столкнёт. Это
не дубликаты: схема трактует второе наблюдение как correction со ссылкой
`supersedes_snapshot_id`. Слияние — смысловой вопрос, а не технический.

## Decision

### Размещение

Rendezvous-хеширование (HRW) внутри **capability-пулов**. Сервер 2 раздаёт
только список членов и фактор репликации `R` на площадку. Аккаунт назначается
top-`R` серверам по убыванию `hash(account_id, server_id)` среди тех, у кого
есть учётные данные этой площадки.

Чистый шардинг — это `R = 1`. Шардинг с копиями — `R = 2`. Полное дублирование —
`R = N`. Одна политика покрывает все три требуемых режима.

Централизованного учёта по каждому аккаунту нет. Смена состава двигает `1/N`
аккаунтов. При недоступности Сервера 2 каждый Сервер 1 продолжает работать по
последнему известному списку — сбор не останавливается.

### Слияние

На бакет сохраняется ровно одно наблюдение. Победитель выбирается
детерминированно, в порядке:

1. качество наблюдения (`ObservationQuality`);
2. полнота метрик — меньше `NULL` побеждает;
3. ранний `collected_at`;
4. `producer_id` как устойчивый tie-breaker.

Проигравшее наблюдение отбрасывается на Сервере 2 и остаётся на своём Сервере 1
как evidence. `correction_sequence` сохраняет прежний смысл — «мы пересмотрели
собственный замер», — и не используется для расхождений между производителями.

Закрытие пропусков получается само: если один сервер бакет пропустил,
наблюдение другого оказывается единственным и побеждает без особого случая.

## Consequences

Дедупликация опирается на детерминированные `uuid5`-идентификаторы, которые уже
есть: одна и та же публикация у разных производителей получает один
`publication_id`.

Появляется control plane — состав, heartbeat и фактор репликации, — которого
раньше не было. Это отдельная поверхность отказов; её худший случай ограничен
тем, что устаревший список приводит к лишнему дублированию или к временному
пропуску части аккаунтов, но не к потере уже собранных данных.

При `R > 1` расход квот площадок растёт в `R` раз. Для ВК это связывающее
ограничение раньше, чем CPU: `VK_REQUESTS_PER_SECOND` по умолчанию 3. Фактор
репликации задаётся на площадку именно поэтому.

Расхождения между производителями в одном бакете — наблюдаемая величина:
частота и амплитуда попадают в метрики. Систематическое расхождение означает
проблему сбора, а не нормальную работу.
