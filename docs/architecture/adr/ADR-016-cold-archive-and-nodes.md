# ADR-016. Холодный архив поколениями, серверы и политики из панели

Статус: принято, 04.10.2026.

## Контекст

Замеры постов растут на 0,3–0,4 ГБ в сутки, а старые посты должны оставаться
доступными на сайте целиком. Удалять данные нельзя. Резервные копии и архив
должны лежать на нескольких серверах, и администратор сам выбирает, где именно.
Серверы-сборщики подключаются без правки окружения и без перезапуска служб.

## Решение

**Холодный архив — поколения месяца партиции** (месяца публикации). Месяц
созревает, когда со дня его конца прошёл срок `coldAfterDays` (не меньше 30)
и все его посты прошли финальный анализ. Конвейер
(`operations/cold_archive/pipeline.py`) переводит один месяц за запуск:

1. Черновик файла просмотра строится без блокировок.
2. Месяц закрывается для записи, выгружается полный Parquet v3 с проверенным
   манифестом, затем дописывается черновик.
3. Файлы регистрируются в хранилище, и агент копирует полный файл на другой
   сервер.
4. Подтверждённая копия становится аттестацией, после чего
   `drop_publication_metric_partition_v22` удаляет партицию.

После удаления месяц снова открыт: поздние контрольные замеры ложатся в новую
партицию и уходят следующим поколением. Месяц закрыт не дольше
`COLD_ARCHIVE_FENCE_MINUTES` (120). Если копии к этому сроку нет, месяц
открывается, а файлы поколения выводятся из оборота. Вечное закрытие сломало
бы перенос с Сервера 1: батчи с поздними замерами повторялись бы бесконечно.

**Два файла на поколение.**
- Полный Parquet нужен для восстановления. Он лежит на серверах `archiveNodes`,
  их минимум два.
- Файл просмотра — SQLite с готовой выдачей истории каждого поста в xz,
  около 82 байт на замер против примерно 990 в горячей таблице. Он всегда лежит
  на основном сервере: API и работник анализа читают его стандартной
  библиотекой за миллисекунды. `pyarrow` нужен только конвейеру.

**Серверы и копии.**
- Реестр `server_node`: имя сервера совпадает с именем в mTLS-сертификате его
  отправителя.
- Каждый сервер, кроме основного, раз в минуту запускает агента
  (`operations/storage/agent.py`, только stdlib). Агент сообщает о дисках,
  памяти, службах и файлах, получает задания на копирование и политику сбора.
- Файлы передаются кусками по 8 МБ через приёмник переноса (`/node/v1/*`),
  с докачкой и сверкой SHA-256. Все передачи идут через основной сервер.
- Где лежать копиям, решает чистая функция `reconcile.plan`. Лишняя копия
  удаляется только тогда, когда все нужные копии сверены. Копия не ложится на
  сервер, если после неё свободного места останется меньше его запаса.

**Политики** (`runtime_policy`) меняются из панели без перезапуска служб:
- `collection` — сборщики применяют её с ближайшего цикла через `runtime.json`
  агента;
- `storage` — срок горячего хранения, число копий и серверы для них;
- `analysis` — срок финального анализа, работник перечитывает его раз в минуту.

Пустые значения означают значения окружения служб, поэтому миграция ничего не
меняет до решения администратора.

**Повторный анализ архива.** Задание панели снимает заморозку с постов месяца,
а обычный работник анализа делает им финальный анализ заново по ряду из
архива и поздних строк базы.

## Последствия

- Архивный пост открывается из файла просмотра. Если файл недоступен, API
  отвечает 503, а работник анализа ставит посту ошибку с повтором. Обрывок
  ряда никогда не анализируется.
- Сравнение постов и недельные приросты на странице аккаунта считаются по
  горячей таблице. Для постов архивного месяца там видны только поздние
  замеры, а приросты первых суток в сравнении будут неполными.
- Новый сервер подключается так: подготовить его (сертификат, сборщик, агент)
  и добавить в панели. Перераспределение аккаунтов делает рандеву-хеш
  сборщиков.
