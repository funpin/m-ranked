# API-интеграции m-ranked

Обновлено: 1 сентября 2026.

Секреты задаются только в серверном `.env`, которому нужны права `600`. Их
нельзя вводить через веб-панель, добавлять в Git, логи или скриншоты. Интерфейс
показывает только состояние «подключено / нужна настройка».

## Telegram

Публичный режим `DATA_SOURCE=public_web` не требует API-токена, но даёт только
публично отображаемые показатели. Чтобы добавить точный счётчик комментариев
без регистрации приложения на `my.telegram.org`, используется авторизованная
сессия неизменённого официального Telegram Web K:

```dotenv
DATA_SOURCE=telegram_web
TELEGRAM_WEB_PROFILE_PATH=/opt/telegram-reaction-monitor/data/telegram-web-profile
TELEGRAM_WEB_CONCURRENCY=3
PLAYWRIGHT_BROWSERS_PATH=/opt/telegram-reaction-monitor/data/ms-playwright
```

После установки Python-зависимостей один раз устанавливается Chromium и
выполняется вход по номеру. Сборщик на это время должен быть остановлен, потому
что два процесса не могут одновременно открыть один профиль браузера:

```bash
PLAYWRIGHT_BROWSERS_PATH=/opt/telegram-reaction-monitor/data/ms-playwright \
  .venv/bin/python -m playwright install --with-deps chromium
systemctl stop m-ranked-collector.service
sudo -u telegram-monitor .venv/bin/python -m app auth-web
systemctl start m-ranked-collector.service
```

Команда запросит номер с кодом страны, код Telegram и, если включён, пароль
двухэтапной аутентификации. Они вводятся в терминале и не записываются в `.env`.
Профиль браузера является секретом аккаунта; каталог должен принадлежать
`telegram-monitor`, иметь права `700`, не попадать в Git и резервные копии без
шифрования.

Этот режим сохраняет быстрый сбор ленты, просмотров и реакций с официальных
страниц `t.me`, а только необходимые сообщения каждого канала одним пакетом
обновляет внутри авторизованного Telegram Web. Из них берётся точное поле
`replies`. Внешние агрегаторы и публичные сторонние источники не используются.
Внутренние объекты Web K не являются стабильным публичным API Telegram, поэтому
после крупных обновлений веб-клиента интеграции может понадобиться адаптация.

Альтернативный точный MTProto-сбор требует:

```dotenv
DATA_SOURCE=mtproto
TELEGRAM_API_ID=...
TELEGRAM_API_HASH=...
TELEGRAM_SESSION_PATH=data/telegram.session
```

`API ID` и `API hash` создаются для аккаунта на `my.telegram.org`. После этого
один раз выполняется `.venv/bin/python -m app auth`; файл сессии также является
секретом и не должен попадать в Git.

MTProto работает через отдельную обычную пользовательскую сессию, аналогично
MAX, но Telegram требует `API ID` и `API hash` для любого стороннего клиента.
Сборщик опрашивает каналы параллельно и одним пакетным запросом обновляет все
публикации канала, для которых наступил очередной интервал. Из ответа берутся
точные счётчики просмотров, реакций и комментариев (`replies`). Публичная
HTML-страница числовой счётчик комментариев не отдаёт.

Вариант с чужими или извлечёнными из официальных клиентов `API ID/API hash` не
используется: он выдаёт сторонний клиент за официальный и создаёт лишний риск
ограничения аккаунта.

Пересылка из другого Telegram-канала сохраняется как признак «репост». Пересылка
из того же канала и сообщение, пересланное от пользователя, репостом канала не
считаются. Публичный HTML-режим определяет признак по блоку источника пересылки.

## ВКонтакте

```dotenv
VK_ACCESS_TOKEN=...
VK_API_VERSION=5.199
```

Сборщик использует read-only методы `groups.getById`, `wall.get` и
`wall.getById`. В базу пишутся просмотры, likes, комментарии и репосты.
Отсутствие токена полностью отключает VK-опрос, не затрагивая другие площадки.

Для обычного поста используется пара `owner_id_post_id`. В совместной
публикации VK может вернуть канонический ID первого автора; тогда m-ranked
находит `coowner_post_id` отслеживаемого сообщества, показывает именно его
номер и отдельно сохраняет признак совместной публикации и количество других
авторов.

## MAX

```dotenv
MAX_USER_PHONE=+79990000000
MAX_USER_FIRST_NAME=Monitor
MAX_USER_LAST_NAME=
MAX_SESSION_PATH=/opt/telegram-reaction-monitor/data/max.session.db
```

Используется отдельный обычный MAX-аккаунт, а не бот. На сервере после установки
зависимостей нужно один раз интерактивно авторизовать его по SMS-коду:

```bash
.venv/bin/python -m app auth-max
```

Если номер ещё не зарегистрирован в MAX, `MAX_USER_FIRST_NAME` обязателен:
клиент создаст профиль после подтверждения SMS. Для существующего аккаунта имя
и фамилия игнорируются.

После успешной авторизации перезапустите основной сервис, чтобы планировщик
подключил MAX-сборщик.

Файл сессии является секретом: нужны права `600`, резервное копирование и
исключение из Git. Для мониторинга в `/manage` достаточно публичной ссылки
канала. При первом опросе аккаунт подписывается на канал, сохраняет его
числовой `chat_id`, а дальше обновляет историю и точечно запрашивает старые
публикации, когда для них наступил следующий возрастной интервал. Эмулятор
Android не нужен: клиент авторизуется как desktop-устройство и работает прямо
на macOS или Linux-сервере.

Сохраняются просмотры, общее число реакций и разбивка реакций по типам.
Публичная ссылка публикации строится из имени канала и числового 64-битного
ID сообщения: ID кодируется в восемь байт big-endian, затем в base64url без
завершающих `=` (`117200531645733298` → `AaBhQzg7GbI`).
Для постов с подключённым обсуждением сохраняется явный счётчик комментариев
из кнопки MAX; однозначная кнопка «Прокомментировать» означает ноль, а кнопка
без числа остаётся `NULL`. Числовой счётчик репостов остаётся `NULL`, пока
пользовательский протокол его не отдаёт. Ссылка типа `forward` из другого
канала помечает саму публикацию как репост.

Важно: это не официальный Bot API, а неофициальный клиент внутреннего протокола
[PyMax](https://github.com/MaxApiTeam/PyMax). Его API может измениться, аккаунт
может быть ограничен, а пункт 4.3.7 [пользовательского соглашения MAX](https://legal.max.ru/ps)
запрещает автоматизированный сбор без специального разрешения компании.
Используйте отдельный аккаунт и запускайте интеграцию только после принятия
этого риска или получения разрешения MAX.

## Rutube

```dotenv
RUTUBE_PUBLIC_API_ENABLED=true
RUTUBE_API_BASE=https://rutube.ru/api
```

Официальные публичные endpoint не требуют токена. Фид видео отдаёт `hits`
(просмотры), `/numerator/video/{id}/vote` — число положительных оценок, а
`/v2/comments/video/{id}/` — число комментариев. Запросы метрик одного цикла
выполняются параллельно с ограничением конкурентности. Если отдельный endpoint
временно недоступен или не содержит показателя, значение остаётся `NULL`.
Репосты публичным API не предоставляются и также не подменяются нулём.

## Расписание публикаций

- Telegram, VK и MAX: 5 минут в первые сутки, 15 минут на 2–3-и сутки,
  30 минут на 4–6-е сутки и 1 час начиная с 7-х суток.
- Rutube: 1 час в первые трое суток, затем 3 / 6 / 12 часов для диапазонов
  4–6, 7–13 и 14+ суток соответственно.

Каждый сборщик работает в собственной задаче планировщика. Это не делает
внешние API безлимитными: ограничения конкурентности и возрастные интервалы
сохраняются отдельно для каждой площадки.

## Проверка после установки секретов

```bash
.venv/bin/python -m app poll-now
curl -fsS http://127.0.0.1:8090/health
```

`/health` показывает только булевый статус конфигурации, время, длительность и
число ошибок последнего цикла каждой площадки. Номер телефона, токены и файлы
сессий туда не входят.
