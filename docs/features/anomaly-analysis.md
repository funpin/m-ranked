# Анализ аномальной динамики

Модуль `anomaly_analysis` ищет в динамике публичных счётчиков поста
(просмотры, реакции, комментарии, репосты) признаки искусственной
активности, выставляет посту уровень и объясняет его формулами и отметками
на графике. Термины — по [ADR-006](../architecture/adr/ADR-006-anomaly-terminology.md),
решения — [ADR-014](../architecture/adr/ADR-014-anomaly-analysis-v2.md),
методы и пороги — [описание методов v2](../research/anomaly-methods-v2.md).

## Что видит пользователь

На странице поста — карточка «Анализ динамики», свёрнутая до одной строки:
символ и название уровня, число признаков, время анализа. Развёрнутая
показывает по каждому признаку формулу с числами, интервал и масштаб,
мини-график, честные альтернативные объяснения; ниже — качество данных,
легенда символов, блок «Методика» и оговорку. На основных графиках интервал
признака подсвечен полупрозрачной полосой с символом, границы отмечены
ромбами; «Показать на графике» подсвечивает выбранный признак.

| Уровень | Название |
|---|---|
| 0 | нет признаков |
| 1 | слабый сигнал |
| 2 | выраженная аномалия |
| 3 | признаки искусственной активности |

Флаг `ANOMALY_REPORT_VISIBLE=false` в `web.env` скрывает карточку и отметки —
тихий режим первой выкатки. По умолчанию отчёт показан.

## API

- `GET /api/v1/publications/{id}/anomaly-analysis` — одна строка
  `analytics.post_anomaly_state`: уровень, до шести признаков со словами,
  качество данных, время анализа, отставание, версии нормы и детекторов,
  статус проверки, оговорка. Пост без анализа — `200` с `level = null` и
  `status = pending`. Ответ идёт через общий кэш `serve()` с тегом
  `analysis`: уведомления о новых замерах его не сбрасывают.
- `POST /api/v1/admin/publications/{id}/anomaly-signals` и
  `POST /api/v1/admin/anomaly-signals/{findingId}/reviews` — команды ручных
  пометок модели v1 на её таблицах. Они не развиваются и уходят вместе с
  удалением v1 (`db/migrations/pending/0039…`).

## Как работает

- **Работник** (`python -m anomaly_analysis`, юнит
  `m-ranked-target-anomaly-analysis.service`) сам ставит в очередь посты окна
  отслеживания, берёт по 50 самых свежих просроченных, читает их ряды одним
  запросом, готовит сетки, прогоняет детекторы, собирает уровень и пишет
  вывод; журнал `analytics.post_anomaly_log` пополняется только при смене
  вывода. Расписание — от 15 минут для свежих постов до 3 часов на 7–30
  сутках (RuTube — от 3 до 24 часов), и только если пришло три новых замера.
- **Покрытие замерами.** Успешный цикл сбора аккаунта сам по себе не доказывает
  чтение конкретного поста. Отсутствующие замеры не превращаются в нули или
  плато. Пробелы учитываются отдельно по метрике: отсутствие просмотров не
  скрывает измеренный скачок собственных реакций.
- **Точность Telegram.** Целые числа и сокращённые `K/M/B` различаются отдельно
  для просмотров и реакций. Исторические округлённые значения не объявляются
  точными задним числом. При сохранённом составе реакций крупный скачок можно
  подтвердить даже по консервативным границам каждого слагаемого.
- **Ранние скачки.** Сравниваются реальные замеры, включая соседние пятиминутные,
  и последующие три часа. Начальный ноль не придумывается; норма аккаунта и
  модель первых суток для этой проверки не нужны. У репостов отдельная
  проверка позднего прироста собственных реакций не использует просмотры источника.
- **Короткий рывок с плато.** Контролируются и десятки реакций. Достаточный
  объём за короткий интервал, подтверждённое плато и отрыв от продолжающегося
  роста просмотров дают уровень 3 одним составным признаком. Повторяемость
  таких рывков не превращает их в норму канала. Крупный поздний скачок просмотров
  с резким плато проверяется отдельно. Если реакции уже присутствовали в первом
  раннем замере, формулировка сообщает именно это, без придуманного нуля.
- **Неполные исторические данные.** Сохранённая форма собственных реакций
  может дать слабый сигнал даже при неизвестной точности. Платные звёзды
  вычитаются из полного согласованного состава; их наличие не скрывает скачок
  обычных реакций. Пропуск опроса внутри рывка запрещает оценивать его скорость.
  Более поздний пропуск не стирает слабый сигнал, если сохранённые наблюдения
  подтверждают замедление, а интервалы между ними не превышают полутора часов.
- **Превышение в Telegram.** Правило 1:1 действует и для округлённых счётчиков.
  Пересечение диапазонов оставляет слабый сигнал; неизвестные и платные реакции
  исключены. Это сравнение счётчиков, а не утверждение о числе людей.
- **Посты в очереди.** Работник ставит в очередь все посты за 75 суток
  (`ANOMALY_SEED_WINDOW_HOURS`), а не только окно отслеживания: у каждого
  поста на сайте есть вывод. Пост старше окна получает один финальный анализ.
- **Разовая перепроверка** (`python -m anomaly_analysis.backfill --days 35`)
  после смены методики: аккаунт за аккаунтом, с агрегатами аккаунта на всё
  окно — работник смотрит синхронность только за трое суток и старое событие
  заново не нашёл бы. Порядок — в ранбуке.
- **Нормы** (`python -m anomaly_analysis.norms_job`, ночной таймер) строятся
  из чистых постов 60 суток, проверяются эталоном и дрейфом; работник
  переходит на новую принятую версию сам.
- **Хранение**: `analytics.post_anomaly_state`, `analytics.post_anomaly_log`,
  `analytics.anomaly_norm_version`, `analytics.anomaly_norm` (миграция
  `0036`). Роль работника — `analytics_worker`; API читает только состояние.

Выкатка и откат — [`operations/runbooks/ANOMALY.md`](../../operations/runbooks/ANOMALY.md).
